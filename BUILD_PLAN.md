### Memory (lesson from 2026-11-15)

At 20:01 on 2026-11-15 the kernel's out-of-memory killer stopped a build. `soong_build`, the analysis step that runs before any compiling, had reached **about 28 GB of RAM** (`anon-rss:28468104kB` in `journalctl -k`). With 29 GiB of RAM and 8 GiB of swap, nothing was left. Because the build had been started from a Claude session, systemd counted it as part of the Claude app's process group (`app-com.anthropic.Claude-*.scope`), so **the Claude app was killed too**.

Rules for future builds:
- **Swap: 40 GiB.** [scripts/grow-swap.sh](scripts/grow-swap.sh) resizes `/swap.img` in place (`sudo scripts/grow-swap.sh`, or `SIZE=48G` for more). `/etc/fstab` already points at `/swap.img`, so the new size survives reboots. Check with `swapon --show`. Status: script written, **not run yet** (it needs `sudo`).
- **Run every build in its own systemd scope**, so that running out of memory kills only the build, never the terminal or the Claude app. [scripts/build-nevada.sh](scripts/build-nevada.sh) now does this itself: it re-runs inside `systemd-run --user --scope` as a unit named `lineage-build-<timestamp>`, capped at `MemoryMax=26G` and `MemorySwapMax=40G` (change with `MEM_MAX=` / `SWAP_MAX=`, skip with `NO_SCOPE=1`). Tested 2026-11-15: the scope sits outside the Claude app's group, and the caps apply. Any build run by hand with `m`/`mka` should be wrapped the same way.
- Close browsers and other heavy apps while `soong_build` runs (the first few minutes). Lowering `-j` does not help with this step, because `soong_build` is a single process. It only helps during the compile that follows.
- If a build dies with no error in `~/lineage/build.log`, check `journalctl -k | grep -i "killed process"` first.

### Whole-laptop power-off (2026-11-15 22:03)

The 4th build (attempt 4, at 57%, step 112,853 of 197,761, about 1h35m in) ended because **the whole laptop switched off**. It was not a build error and not out of memory.
- The journal for that boot just stops at 22:03:41. Messages were still arriving up to that second, and there is no shutdown sequence. The next boot came up at 22:03:59. `~/lineage/build.log` ends in null bytes, the usual sign of a hard power cut.
- The next boot's kernel log records why (AMD CPUs report this): `Previous system reset reason [0x00200800]: ACPI power state transition occurred`. A normal reboot shows `software wrote 0x6 to reset control register 0xCF9` instead. So the firmware cut the power. It was **not** the CPU's own thermal trip, a 4-second power-button press, a machine-check or data-fabric error (each has its own code), a kernel panic, or an OOM kill.
- On mains power with the battery full, and no power-supply events in the log.
- Most likely cause: **the embedded controller (EC) of the MSI Creator A16 AI+ shutting down for heat**, after about 1.5 h at 93% CPU on the `performance` profile (5 GHz). Not proven: no temperatures were logged during the build. Signs that point to heat: at idle the SSD's Sensor 1 already reads 64 °C, the BIOS is old (`E15FKAMS.309`, 2024-09-20), `thermald` does not support this CPU, and the MSI fan sensors read 0 RPM, so Linux cannot see or control the fans.
- Not the cause: the steady `AER ... BadDLLP/BadTLP` messages come from the Realtek 2.5GbE port (`00:02.2`). They appear on every boot, idle ones too, and are correctable.
- Rules until this is understood: log temperatures during builds (k10temp `Tctl`, nvme, acpitz), so the next crash shows what heated up. Prefer the `balanced` power profile (`powerprofilesctl set balanced`) or a lower `-j` for long builds. Keep the vents clear and the laptop raised. Check MSI for a newer BIOS/EC firmware. Ninja resumes where it stopped, so a crash costs only the time to restart.

**Aftermath: a power cut leaves corrupt build outputs (found 2026-11-15 22:41).** The restart at 22:14 failed after 5 minutes in `adbd` with `undefined symbol` errors from protobuf. The real cause was `libprotobuf-cpp-lite.a`, which was **0 bytes**, stamped 22:03. The crash lost data that was not yet flushed to disk. About 12,400 files in `out/` were written in the last minutes before the cut (644 of them empty), and Ninja treats a present file as up to date, so it kept using the broken ones. The `build.log` full of null bytes was the visible sign of the same problem.
- **After any hard crash or power cut, delete every output written in the last few minutes before it**, then restart. Ninja rebuilds what is missing, and ccache keeps this cheap. Run from `~/lineage/android/out`, with the right times: `find . -type f -newermt "<crash time minus 10 min>" ! -newermt "<crash time plus 1 min>" ! -name ".ninja_*" ! -name "*.log" -delete`. Done 2026-11-15 for 21:55–22:05 (23,079 files).
- A link error about undefined symbols from a library that is on the link line, in a build that previously passed that step, points to a 0-byte or truncated `.a`/`.o`. Check with `ls -la` and `llvm-ar t`.

This Windows PC stays useful for flashing and recovery: `adb`, `fastboot` and Motorola Software Fix already work here, and it holds the stock firmware. It is a fallback build machine too (32 GB RAM, i7-9700K, 545 GB free on D:, WSL2 installed but no distro).

*Lessons from this attempt*
- Before any flash, **prove the USB link with a large transfer**, not just `getvar`. (Small commands and an 8-16 MB write worked right up until the 64 MiB ones.) A short, known-data USB-A to USB-C cable on a USB-A port is the safest.
- **Never flash `vbmeta` before the images it covers.** Do the big images first, `vbmeta` last. Here `vbmeta` was flashed first and was already in place when the big writes failed.
- The plan to flash our images onto the **current** slot `_b` (so sideload writes the full system to `_a`, the way the LineageOS guide does it) means the only known-good slot is the one being modified. Next time, if a better safety net is wanted, check `_a` first by booting it once.
- fastboot 34.0.5 (Debian) fails with `Error reading sparse file` on `-S` chunks of these images. `img2simg` sparse files did not help (fastboot expanded them back to 64 MiB). The AOSP-built `fastboot` 36.0.0 (`~/lineage/android/out/host/linux-x86/bin/fastboot`) failed the same way, because the link itself was failing.
- The user decided (2026-11-17) not to back up the IMEI/`nvdata`/`persist` partitions.

## Risks to keep in mind

- **Bricking.** A bad flash can leave the phone unusable. A MediaTek phone can often be recovered with stock firmware, but we should not assume it. Test with `fastboot boot` first and keep the phone you depend on as a spare if possible.
- **Locked-down carrier model.** XT2613-1 is the US carrier variant (retus). Motorola's unlock portal may refuse it even though the OEM unlocking toggle is available. We find out when we request the code.
- **Calls and mobile data** on MediaTek phones depend on proprietary IMS pieces; they are the most common failure area.
- **The `nevada` tree is unproven.** It reportedly compiles, but we have no evidence it boots.
- **Android 16 vendor mismatch.** The phone's vendor side is Android 13 based, so the tree and blobs must match it.
